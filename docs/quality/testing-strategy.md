# راهبرد تست — testing-strategy

> **منبع:** سند مادر v2.5 فصل ۱۲. پشته: **Vitest** (unit) + **Vitest با PostgreSQL واقعی**
> (integration — Testcontainers/سرویس CI) + **Playwright** (E2E) + **fast-check** (خاصیت‌محور).
> تستی که گذار مالی/تحویل را نمی‌سنجد، نوشته نشده تلقی می‌شود. غیرفعال‌کردن تست برای
> سبزکردن CI ممنوع است.

## زیرساخت

- **integration فقط روی PostgreSQL واقعی** — ایندکس جزئی، تریگر، ستون تولیدشده و `ON CONFLICT` روی SQLite/mock درست تست نمی‌شوند.
- دادهٔ تست همیشه fixtures مصنوعی — هرگز دادهٔ واقعی مشتری (خصوصی‌بودن ریپو جایگزین حفاظت داده نیست).
- دو تست خرابی اجباری: (۱) کشتن worker وسط ارسال پیامک → job قابل‌ادامه بدون ارسال تکراری؛ (۲) قطع DB وسط commit اصلاح مبلغ → rollback کامل + اجرای مجدد idempotent.

## تست‌های واحد (بخش‌های کلیدی)

- نرمال‌سازی ارقام فارسی/عربی + حفظ صفر ابتدایی؛ نرمال‌سازی موبایل (+98/0098/912/ارقام فارسی → 09xxxxxxxxx)
- **محاسبهٔ مبلغ:** دو مثال طلایی (۸۰٬۶۸۶٬۴۴۵→۸۰٬۷۰۰٬۰۰۰؛ ۱۳٬۷۱۲٬۵۰۰→۱۳٬۷۵۰٬۰۰۰) + مبلغ مابقی بدون گرد مجدد
- **تست خاصیت‌محور (fast-check):** خروجی گرد همیشه مضرب تنظیم و ≥ ورودی؛ مابقی نامنفی؛ فاز مشتق هر ترکیب تصادفی ∈ فازهای مجاز ∪ NEEDS_ATTENTION
- استخراج شماره/سال از نام PDF با هر دو الگوی regex
- `parseWaybillDate` جدول‌محور: سریال معتبر/نامعتبر، شمسی با نقطه/خط مورب، ارقام فارسی، مرز ۱۴۰۳/۱۲/۳۰–۱۴۰۴/۰۱/۰۱، کبیسه؛ **عدد خام ۱۴۰۵ = INVALID_DATE_FORMAT**
- رندر قالب تعهدنامه: متغیر resolve‌نشده = خطا؛ **تست golden بایت‌به‌بایت** هر قالب ACTIVE با دادهٔ نمونهٔ ثابت
- فاز مشتق شامل RESIDUAL_DUE / REFUND_RECORDED / REFUND_SETTLED / DECLINED
- `canRelease` و کدهای شرط‌های برقرارنشده
- آداپترهای درگاه با mock HTTP (fixtures رسمی در `tests/fixtures/gateways/`): init/verify/inquiry، نگاشت کد خطا، تبدیل ریال↔تومان زرین‌پال، `101` = موفق idempotent
- اعتبارسنجی کارت/شبا: Luhn، MOD-97، نگاشت bank_code → آیکون/نام

## تست‌های یکپارچه (موارد تعیین‌کننده)

- Import کل مسیر ۱۱گامی؛ عبور ردیف صفر/صفر بدون رکورد؛ خطای فهرست‌وار ستون غایب؛ نگاشت شرکت دیگر
- duplicate و idempotency فایل (file_hash)؛ کلید سال تهی → DUPLICATE
- اتصال PDF: خودکار بدون تأیید انسانی در تطبیق یکتا؛ ۱:۱ (فایل دوم → ALREADY_ATTACHED)؛ کاندید باطل → MANUAL_REVIEW
- تأیید/رد پرداخت با دلیل (بدون دلیل = خطا)؛ **اصلاح مبلغ: کم‌پرداخت (لینک مابقی بدون امضای مجدد) + اضافه‌پرداخت (پیامک)**
- **بازگشت وجه فقط پس از تأیید سرپرست؛ رد در DB سقف با تریگر (تست هم‌زمان دو ثبت)**
- قیدهای فیزیکی: CHECK آزادسازی، ایندکس مجوز فعال، FK مرکب (رکورد فرزند ناسازگار رد شود)
- گاردها: `OVERPAYMENT_REQUIRES_DISCREPANCY` · `AMOUNT_CHANGED` · `WAYBILL_NOT_ACTIVE` · `COMMITMENT_NOT_ACCEPTED` (ثبت پرداخت قبل از پذیرش در ENFORCED)
- import ناهمگام: فایل ۶۰۰ ردیفی → COMMITTING → poll → COMMITTED؛ کشتن worker وسط commit → اجرای مجدد idempotent
- idempotency: همان کلید یک رکورد؛ بازپخش پاسخ؛ کلید + بدنهٔ متفاوت = `IDEMPOTENCY_KEY_REUSED`
- **چرخهٔ درگاه با PSP ماک:** init → INITIATED → callback → وریفای s2s → APPROVED خودکار + پیامک + audit؛ callback تکراری idempotent؛ مبلغ دستکاری = MISMATCH؛ مرجع تکراری = برخورد قید؛ state نامعتبر = INVALID؛ دو init هم‌زمان = یکی رد؛ UNKNOWN → job استعلام؛ انقضای ۲۰ دقیقه؛ تغییر current_amount_id وسط تلاش = CANCELLED/AMOUNT_CHANGED
- کارت‌ها: شبای نامعتبر رد؛ کارت ۱۵رقمی رد؛ کارت غیرفعال در API راننده برنمی‌گردد؛ نمایش فقط با نشست؛ payout_card_id الزامی؛ ماسک در لاگ
- پرداخت درگاهی APPROVED در صف بررسی فقط خواندنی → endpoint review رد با `PAYMENT_AUTO_VERIFIED`
- سوئیچ خودکار پیامک فراز→ملی‌پیامک + دلیل ساده؛ اعلان داخلی در همان تراکنش

## E2E (Playwright — جریان‌های بحرانی)

```text
Admin login → import Excel → upload PDFs → matching → driver link →
driver opens link → OTP → view amount → read & sign commitment (گام ۲) →
pay via gateway (sandbox) → server-side verify → driver downloads PDF
```

سناریوی جایگزین گام ۳: ثبت دستی (شماره تراکنش + رسید) → تأیید متصدی → دانلود.

سناریوهای خطا: PDF بدون اکسل · اکسل بدون PDF · شمارهٔ تکراری · پرداخت مشابه · لینک منقضی ·
دانلود قبل از تأیید · کاربر بدون مجوز · **دو بررسی‌کنندهٔ هم‌زمان (اولی معتبر، دومی 409 PAYMENT_STATE_CONFLICT)** ·
مبلغ اشتباه (هر دو مسیر) · ابطال پس از پرداخت + بازگشت وجه · **قطع اینترنت وسط مسیر راننده → ادامه از همان مرحله** ·
**رد تعهدنامه در ENFORCED → AWAITING_COMMITMENT + اعلان + پرداخت رد** · **درگاه ناموفق → مسیر کارت‌به‌کارت باز** ·
**UNKNOWN → قفل دکمهٔ پرداخت مجدد تا نتیجهٔ استعلام**

## بار و هم‌زمانی

- **۵۰ نشست هم‌زمان راننده:** ورود OTP و ثبت پرداخت موازی بدون مسابقه (E2E با ۵۰ نشست مرورگری).
- **بار ۳ برابری (۱۵۰ نشست / ۶۰۰ بارنامه در روز):** با k6 روی APIهای پورتال در staging جدا و seed مشخص — فقط کندی تدریجی مجاز است؛ خطا/از دست رفتن داده ممنوع.
- **دو بررسی‌کننده با تاخیر تزریقی (deterministic):** فقط اولین تصمیم معتبر.
- ۵۰۰ ردیف import <۶۰ ثانیه؛ ۵۰۰ PDF <۵ دقیقه.

## ماتریس دسترسی endpoint×نقش (CI)

همهٔ مسیرهای api-contracts در برابر: OWNER/MANAGER/SUPERVISOR/OPERATOR (با/بدون مجوز مستقل)،
TECH_ADMIN، راننده (با/بدون نشست)، بی‌نشست — انتظار ۲۰۰/۴۰۱/۴۰۳ جدول‌محور اجرا می‌شود؛
**فهرست ماتریس از کاتالوگ endpoint تولید می‌شود تا endpoint جدید بدون ردیف ماتریس، CI را بشکند.**

## تعریف Done (نمونه‌ها)

**ورود PDF** Done است وقتی: فایل غیر-PDF رد شود · سقف حجم · نام بدون شماره مدیریت شود ·
ارقام فارسی نرمال · تکراری/چندمعنا تشخیص · اتصال اشتباه قابل لغو · audit ثبت شود ·
دسترسی کنترل شود · E2E باشد · خطای فارسی قابل‌فهم نمایش داده شود.

**پرداخت درگاهی** Done است وقتی: وریفای هرگز به callback اعتماد نکند · مبلغ مقایسه شود ·
callback تکراری idempotent · UNKNOWN هرگز FAILED فرض نشود · دو init هم‌زمان یک تلاش ·
PAN ماگسک و اعتبارنامه در هیچ لاگی نباشد · چرخهٔ sandbox + PSP ماک سبز · ردیف ماتریس سبز.
