# قواعد کسب‌وکار (Business Rules) — فایل اجرایی

> **منبع:** سند مادر v2.5 فصل ۴ (۴.۱ تا ۴.۶). این فایل «تنها ورودی پیاده‌سازی» است
> (به همراه data-model / state-transitions / invariants). هر قاعده با شماره تصمیم
> مبدا آمده تا در اختلاف، قابل ردیابی باشد. مثال‌های «قبول/رد» در انتها.

## ۱. تصمیمات قطعی MVP (خلاصه فصل ۴.۱)

| موضوع | قاعده |
|---|---|
| منبع مبلغ | ستون «جمع پرداختی راننده» اکسل + گرد رو به بالا + افزودنی اختیاری؛ ثبت در `waybill_amounts` |
| پرداخت جزئی مسیر عادی | ممنوع |
| مابقی پس از اصلاح | لینک مخصوص، **بدون تأیید و امضای مجدد تعهدنامه** |
| یک پرداخت برای چند بارنامه | ممنوع (تجمیع پرداخت = آیتم ۱.۱+ با batch_id) |
| چند تلاش پرداخت یک بارنامه | مجاز؛ تأیید مالی تکراری نمی‌سازد |
| کم‌پرداخت | لینک مابقی (فرآیند ۶.۵ حالت ۱) |
| اضافه‌پرداخت | پیامک اطلاع‌رسانی + ثبت + تماس با شرکت (حالت ۲) |
| بازگشت وجه | ثبت دستی + تأیید سرپرست (فرآیند ۶.۹) |
| تأیید پرداخت/تحویل | سرپرست عملیات + اپراتورهای دارای مجوز واگذارشده |
| شماره تکراری بارنامه | توقف تطبیق تا رفع ابهام (DUPLICATE) |
| ورود دوباره اکسل | بدون رکورد/مطالبهٔ تکراری (file_hash) |
| تعویض PDF پس از تحویل | فقط اصلاح کنترل‌شده با مجوز `REPLACE_PDF` |

## ۲. سه تصمیم نسخهٔ ۲.۵ (فصل ۴.۶ — بالاترین اولویت)

### تصمیم ۱۹ — تعهدنامه پیش از پرداخت
- زنجیرهٔ راننده: **مشاهده اطلاعات ← پذیرش و امضای تعهدنامه ← پرداخت ← دانلود**.
- در حالت ENFORCED، endpoint ثبت پرداخت (دستی و درگاهی) بدون `commitment_status = ACCEPTED` با کد `COMMITMENT_NOT_ACCEPTED` رد می‌شود.
- ردِ راننده («مخالفم؛ تماس بگیرید») = `DECLINED` + اعلان متصدی + بسته‌ماندن مسیر پرداخت؛ هیچ جریان مالی آغاز نمی‌شود.
- در مسیر مابقی، گام تعهدنامه تکرار نمی‌شود (پذیرش قبلی معتبر است).

### تصمیم ۲۰ — درگاه پرداخت در MVP
- شش ارائه‌دهنده پشت آداپتر واحد `PaymentProvider`: مستقیم (سامان SEP، ملت BPM، پاسارگاد، سداد) + واسط (زرین‌پال، زیبال).
- هر سازمان حداکثر یک درگاه ACTIVE (قید فیزیکی)؛ مدیر از پنل پیکربندی می‌کند.
- مبلغ درخواست همیشه از رکورد جاری `waybill_amounts` — نه ورودی راننده.
- وریفای فقط server-to-server؛ نتیجهٔ موفق = APPROVED خودکار (بدون صف انسانی؛ فقط با برچسب «تأیید خودکار (درگاه)» قابل مشاهده).
- روش‌های دستی همیشه به‌عنوان مسیر جایگزین باقی‌اند.

### تصمیم ۲۱ — کارت‌های واریز گرافیکی
- CRUD کارت‌های سازمان با مجوز `MANAGE_BANK_CARDS`: بانک (آیکون محلی `public/banks/{bank_code}.svg`)، نام/نام خانوادگی صاحب کارت، شماره کارت ۱۶رقمی (Luhn)، شماره حساب، شماره شبا (MOD-97).
- پورتال راننده: کارت گرافیکی کپی‌پذیر (کپی مقدار نرمال‌شده + پیام «کپی شد»)؛ راننده کارت مقصد را انتخاب می‌کند (`payout_card_id` برای کارت‌به‌کارت الزامی).
- پس از واریز: دکمهٔ «پرداخت کردم» + تصویر رسید (≤۵MB) و/یا شماره تراکنش ۴-۲۰ رقمی؛ حداقل یکی الزامی (تنظیم سازمان).

## ۳. زنجیرهٔ مبلغ (فصل ۴.۲) — پیاده‌سازی در یک تابع واحد

```text
۱. مقدار خام ستون «جمع پرداختی راننده» → عدد صحیح ریال (نامنفی؛ منفی/غیرعددی = INVALID ردیف)
۲. گرد شدن رو به بالا به مضرب سازمان (پیش‌فرض ۵۰٬۰۰۰ ریال)
۳. + مبلغ افزودنی در صورت فعال‌بودن (پیش‌فرض ۷۰۰٬۰۰۰ ریال؛ قابل تنظیم لحظهٔ ارسال)
۴. ثبت در waybill_amounts با تفکیک اجزا (raw / rounded / surcharge / amount)
```

- واحد پول **ریال و ثابت**؛ همه‌جا عدد صحیح `BIGINT` (در TS/Zod از `bigint`؛ در JSON رشته).
- «مبلغ مابقی» مجدداً گرد **نمی‌شود**: دقیقاً تفاضل «اصلاح‌شده منهای مجموع پرداخت‌های تأییدشده».
- هیچ مسیری خارج از `waybill_amounts` مبلغ قابل پرداخت نمی‌نویسد؛ هیچ عدد خام اکسلی بدون این زنجیره به راننده نمایش داده نمی‌شود.
- مبلغ دستی متصدی (خارج زنجیره): پاپ‌آپ تأیید محتوا (شماره بارنامه، نام راننده، مبلغ قدیم/جدید، دلیل) پیش از ارسال.
- منبع مبلغ در `waybill_amounts.source`: `EXCEL_CALCULATED / OPERATOR_ENTERED / OPERATOR_CORRECTION` (برای CORRECTION ستون reason اجباری — قید CHECK).

**تست‌های طلایی:** ۸۰٬۶۸۶٬۴۴۵ → ۸۰٬۷۰۰٬۰۰۰ و ۱۳٬۷۱۲٬۵۰۰ → ۱۳٬۷۵۰٬۰۰۰ (ریال).

## ۴. ردیف باطل‌شدهٔ قبلی (پاسخ ۱۳)

ردیفی که «جمع پرداختی راننده» و «وزن بارنامه» هر دو صفرند، پیش از ورود باطل شده:
- هیچ رکورد بارنامه/پیامک/پرداخت/عملیاتی ساخته نمی‌شود؛
- فقط در `import_rows` با `SKIPPED_PREVIOUSLY_CANCELLED` ثبت و در گزارش شمارش می‌شود.

## ۵. اکسل ورودی (پاسخ ۱۲)

- ستون‌های الزامی: نام راننده، تلفن راننده، شماره بارنامه، جمع پرداختی راننده؛ غیبت هرکدام = خطای فهرست‌وار «این فایل فاقد ستون‌های لازم است: …».
- نگاشت ستون‌ها در `excel_column_mappings` هر سازمان (عنوان یا موقعیت)؛ اعتبارسنجی هم در سرویس و هم Zod.
- هر ردیف = یک بارنامهٔ مستقل (شماره‌های متمایز؛ تکراری نیست).
- سقف پذیرش: ۱۵MB / ۵٬۰۰۰ ردیف؛ دامنهٔ ضمانت عملکرد: ۵۰۰ ردیف؛ >۵۰۰ ردیف = ثبت job پس‌زمینه (`COMMITTING` → poll تا `COMMITTED/FAILED`)؛ تراکنش اتمیک حفظ می‌شود.
- فقط `.xls`/`.xlsx`/`.csv` (CSV فقط UTF-8)؛ فرمت ماکرودار رد.
- نرمال‌سازی: ارقام فارسی/عربی؛ موبایل → `09xxxxxxxxx` (حذف +98/0098/98، تکمیل 912…)؛ نامعتبر = INVALID.
- تاریخ: تابع واحد `parseWaybillDate` — اولویت: (۱) سریال اکسل معتبر [۳۰۰۰۰..۶۰۰۰۰]؛ (۲) رشتهٔ شمسی `1405/06/18` یا `1405.06.18` (با ارقام فارسی)؛ (۳) عدد خام خارج بازه = `INVALID_DATE_FORMAT` (عدد خام هرگز «سال» فرض نمی‌شود).
- سلول فرمول‌دار: فقط مقدار cached (`FORMULA_NOT_CACHED`)؛ سلول ادغام‌شده: خطای صریح؛ BOM پذیرفته و حذف.
- idempotency فایل: `file_hash`؛ COMMITTED قبلی = رد با `IMPORT_ALREADY_PROCESSED`؛ CANCELLED/FAILED = ورود مجدد مجاز.

## ۶. تطبیق PDF (پاسخ ۱۱ و ۱۲)

- رابطهٔ ۱:۱ — هر بارنامه حداکثر یک PDF فعال (ایندکس یکتای جزئی)؛ فایل دوم = `ALREADY_ATTACHED` → مسیر جایگزینی با مجوز.
- تطبیق **سیستمی و خودکار** (بدون تأیید انسانی) فقط وقتی: شماره از نام استخراج شود + دقیقاً یک کاندید + PDF و بارنامه هر دو آزاد باشند + نوع واقعی PDF (magic bytes) + هش معتبر.
- الگو: `BL[\s-_]*([0-9۰-۹]+)(?:[\s-_]+(\d{2,4}))?` — سال فقط محدودکنندهٔ اولویت، نه کلید.
- دامنهٔ جست‌وجو: کل سازمان (دستهٔ import فقط اولویت است).
- کاندید CANCELLED/ARCHIVED → MANUAL_REVIEW (اتصال خاموش به پروندهٔ ممنوع).

## ۷. اصلاح مبلغ پس از پرداخت (پاسخ ۵ — فرآیند ۶.۵)

**کم‌پرداخت:** ثبت مبلغ جدید با دلیل الزامی (مجوز `CORRECT_AMOUNT_AFTER_PAYMENT`) → مابقی = اصلاح − پرداخت‌های تأییدشده (بدون گرد مجدد) → `RESIDUAL_DUE` → پیامک + لینک مابقی **بدون امضای مجدد** → آزادسازی تا تأیید مابقی مسدود → پرداخت مابقی با `is_residual=true` و `parent_payment_id`.

**اضافه‌پرداخت:** `DISCREPANCY_REVIEW` + ثبت مبلغ دقیق اضافه + پیامک به راننده («مبلغ اضافی … برای بازپس‌گیری با شرکت تماس بگیرید») + اعلان متصدی + در صورت بازگشت، فرآیند ۶.۹.

- گارد تأیید: پرداخت بیش از مانده → `OVERPAYMENT_REQUIRES_DISCREPANCY`.
- گارد `AMOUNT_CHANGED`: اگر `current_amount_id` بین ثبت و تأیید عوض شده → تأیید عادی مسدود.
- تکرار سخت شماره پیگیری (CARD_TO_CARD/POS/BANK_TRANSFER در سازمان) = `PAYMENT_TRACKING_DUPLICATE` (ایندکس یکتای جزئی)؛ تکرار نرم (مبلغ+روش یکسان، ۱۰ دقیقه، همان راننده/بارنامه) = `DISCREPANCY_REVIEW`.

## ۸. بازگشت وجه (پاسخ ۱۳ — فرآیند ۶.۹)

- همیشه دستی؛ هیچ مسیر خودکاری پول حرکت نمی‌کند (استرداد API = آیتم ۱.۱+).
- ثبت (`RECORD_REFUND`) → وضعیت `RECORDED` → تأیید سرپرست (`APPROVE_REFUND`) → `REFUND_SETTLED` + پیامک.
- سقف: بازگشت ≤ مجموع پرداخت‌های تأییدشده (تریگر `check_refund_ceiling` + advisory lock).
- ثبت‌کننده ≠ تأییدکننده (maker-checker)؛ رکورد پس از RECORDED قابل ویرایش نیست (رد با دلیل + رکورد جدید).

## ۹. تعهدنامه (پاسخ ۶ — فصل ۴.۳/۶.۶)

- سیستم قالب `{{variable_key}}`: متغیرها فقط از دادهٔ سرور (driver_name، waybill_number، amount، issue_date…)؛ متغیر resolve‌نشده = خطا و توقف ارسال (`TEMPLATE_VARIABLE_UNRESOLVED`).
- رندر فقط سمت سرور؛ snapshot کامل (`rendered_text`) + `content_hash` در پذیرش؛ تست golden بایت‌به‌بایت هر قالب ACTIVE.
- سه حالت `COMMITMENT_ENFORCEMENT`: OFF → بدون گام؛ SHADOW → گام قبل از پرداخت با «ادامه بدون پذیرش» + ثبت؛ ENFORCED → تنها مسیر پرداخت از پذیرش می‌گذرد. گذار فقط OFF → SHADOW → ENFORCED؛ ENFORCED نیازمند تأیید حقوقی.
- امضای ترسیمی: PNG شفاف، ≤۵۰۰KB، بوم ≥۳۰۰×۱۵۰؛ اعتبارسنجی دوشرطی (≥۱٪ پیکسل ترسیم‌شده و ≥۲۰۰px طول مسیر)؛ سند مستقل `document_type=SIGNATURE`.
- مبنای حقوقی: اقرار الکترونیکی مبتنی بر مالکیت شماره موبایل — واژگان UI صادقانه («اقرار الکترونیکی شما ثبت شد»، نه امضای دیجیتال).
- نسخهٔ قالب تغییرناپذیر است (تریگر)؛ تغییر متن = نسخهٔ جدید + RETIR قدیمی؛ تغییر مؤثر = `RE_ACCEPT_REQUIRED` برای بارنامه‌های آینده.

## ۱۰. اعلان‌ها و پیامک (پاسخ ۱۴ و ۱۶)

- فراز اس‌ام‌اس (اصلی) + ملی‌پیامک (failover خودکار) پشت آداپتر `SmsProvider`؛ مدارشکن (≥۳ خطا در ۶۰ثانیه → open ۵ دقیقه)؛ timeout هر فراخوانی ۱۰ ثانیه؛ ۵ تلاش با backoff.
- SLA: p95 ≤ ۳۰ ثانیه از رویداد تا پذیرش provider.
- پنل ناموفق‌ها با دلیل فارسی ساده + دکمهٔ «ارسال مجدد» و «پیگیری تلفنی».
- مرکز اعلان داخلی الزامی (ناقوس + فهرست + لینک مستقیم)؛ تولید اعلان در همان تراکنش رویداد.
- سقف روزانهٔ سازمان: ۲٬۰۰۰ پیامک (هشدار ۸۰٪؛ سقف → صف‌بندی + اعلان سرپرست).
- قالب‌های پیامک در فاز صفر روی خط واقعی تأیید می‌شوند.

## ۱۱. نگهداری داده (پاسخ ۸)

`KEEP_1Y / KEEP_10Y (پیش‌فرض نصب) / KEEP_CUSTOM / KEEP_FOREVER` — انتخاب مدیر؛ اجرا با job زمان‌بندی‌شده + آرشیو اختیاری + ثبت audit. رکوردهای کوتاه‌عمر (OTP/نشست ≤۳۰ روز، idempotency ۲۴ ساعت) مشمول سیاست نیستند.

## ۱۲. ظرفیت و پایداری (پاسخ ۱۷)

- پیک ~۵۰ رانندهٔ هم‌زمان؛ پردازش ترتیبی هر راننده (قفل سطری، بدون مسابقه روی رکورد).
- ادامه‌پذیری: هیچ فرآیندی به بقای یک درخواست/تب وابسته نیست؛ گام از وضعیت سرور مشتق می‌شود؛ پیش‌نویس فرم راننده در localStorage؛ همهٔ jobها idempotent.
- لاگ با `human_message` + `action_hint` فارسی ساده.

## ۱۳. استقرار (پاسخ ۱۰)

کد مشترک + استقرار و دیتابیس و دامنهٔ جدا برای هر شرکت (Docker Compose)؛ `organization_id` در مدل باقی می‌ماند (مسیر SaaS آینده باز)؛ ابزار `tools/migrate-all.ts` + registry استقرارها.

## مثال‌های قبول/رد

**قاعدهٔ گرد شدن:**
- ✅ `80686445` با مضرب ۵۰۰۰۰ → `80700000` سپس +۷۰۰٬۰۰۰ افزودنی → `81400000`
- ✅ `13712500` → `13750000`
- ❌ `80686445 → 80686000` (گرد رو به پایین ممنوع)
- ❌ `round(80700000 * 1.0086)` (محاسبهٔ اعشاری ممنوع)
- ❌ ذخیرهٔ مبلغ با `float`/`number`

**ترتیب زنجیره (تصمیم ۱۹):**
- ✅ راننده بدون پذیرش تعهدنامه (ENFORCED) → `POST /api/driver/payment` = 4xx `COMMITMENT_NOT_ACCEPTED`
- ✅ راننده پذیرفت → پرداخت درگاهی → وریفای موفق → APPROVED خودکار → دانلود
- ❌ نمایش دکمهٔ پرداخت فعال پیش از پذیرش در ENFORCED (حتی اگر سرویس گارد داشته باشد — UI هم نباید گمراه کند)
- ❌ درخواست امضای مجدد برای پرداخت مابقی

**درگاه (تصمیم ۲۰):**
- ✅ callback زرین‌پال با `Status=OK` → فقط وریفای server-to-server ملاک؛ `code=101` = موفق idempotent
- ✅ مغایرت مبلغ وریفای → `GATEWAY_AMOUNT_MISMATCH` + FAILED
- ❌ اعتماد به پارامترهای callback برای APPROVED
- ❌ تبدیل ریال↔تومان خارج از آداپتر زرین‌پال

**کارت‌ها (تصمیم ۲۱):**
- ✅ کپی شبای `IR` + ۲۴ رقم بدون فاصله
- ❌ نمایش کارت غیرفعال در پورتال راننده
- ❌ ثبت کارت‌به‌کارت بدون `payout_card_id`
